# Моя история — архитектура проекта

## Актуально: независимый пароль/биометрия и страницы капсул — 12 октября 2026

`capsule-biometry.native` предоставляет opt-in после проверки существующего пароля сервером. SecureStore credential привязан к user/family, требует strong OS authentication, отдельный keychainService и device-only accessibility; сохраняется только дополнительный пароль раздела. Marker/index не содержат секретов. Это явное исключение из прежнего RAM-only правила для пароля; AES-ключ/permit/письмо остаются только в RAM. Web stub не сохраняет секрет, iOS Expo Go намеренно отключён. Любая зарегистрированная strong-биометрия подходит; это не идентификация родителя. Очереди/revision защищают logout и поздние native операции. Смена аккаунта очищает credential best effort, но не серверные капсулы. После logout opt-in повторяется.

Закрытый настроенный раздел показывает выбор «Войти по отпечатку» / «Ввести пароль»; обычный пароль не запускает OS scan. Подключение биометрии — отдельный режим с однократным паролем. Оба способа используют прежний server unlock/owner gate/лимитер и 10-minute permit. OS prompt не открывает содержимое до возвращения приложения в active. Старые epoch/scope/foreground guards сохранены.

Новый `list_family_capsules` SECURITY INVOKER endpoint вызывает private checked implementation с прежним frozen/current-owner + permit gate. Ключ не возвращается. 30+1 метаданных, `archived` до пагинации, сортировка updated_at DESC/id ASC и точный курсор с микросекундами; индекс family/archived/time/id. UI FlatList, bound user/family/archive cursor и late-result checks. Старый `family_capsule list` с limit 200 остаётся для совместимости, новый экран его не использует.

Состояния загрузки списка idle/loading/ready/error разделены: read failure не означает отсутствие записей и не отменяет уже подтверждённый save. Before-remove guard и явное подтверждение защищают обычную навигацию из письма, но не блокируют account change/logout. Сохранённые серверные капсулы живут независимо от Auth сессии; несохранённый RAM-only черновик не обещает пережить logout/process death. Подробные проверки/границы: `docs/CAPSULE_BIOMETRY_VERIFICATION.md`.

## Предыдущая версия: owner-only капсулы под отдельным паролем — 12 октября 2026

Правило продукта: **без блокировки по возрасту**. «Семья → Капсула времени» доступна только создателю. В существующей модели onboarding создатель получает `family_members.role='owner'`; в `families` отдельного creator_id нет. При первом создании раздела его owner_id фиксируется. Каждая операция требует и этого owner_id, и текущего owner-членства. Будущую передачу собственности/восстановление после удаления аккаунта проектировать отдельно, не открывать раздел новому role-owner автоматически.

Маршрут `/family/capsules` входит в прежний семейный Stack.Protected; сам экран проверяет роль/scope/focus. Остальные разделы не используют капсулы. Один пароль (8–64 символа, максимум 72 UTF-8 байта из-за bcrypt), пять ошибок/15 минут ограничения на сервере. `unlock` выдаёт случайный 256-bit допуск на 10 минут; сервер хранит SHA-256 и разрешает только один активный допуск. Новый вход/смена пароля/lock отзывают прежний. Восстановление — неперсистентный отдельный Supabase Auth password login того же user_id; server reset требует signed password AMR не старше пяти минут. `user_metadata` для прав не используется.

`moya_private.capsule_vaults` и `family_capsules` — RLS-enabled, без прямых anon/authenticated table grants и policies. Один public **SECURITY INVOKER** wrapper `family_capsule(uuid,text,text,jsonb)` имеет authenticated EXECUTE без PUBLIC/anon. Проверяемая SECURITY DEFINER реализация и Storage helper — в private schema, empty search_path. Per-family advisory lock + share-lock membership предотвращают гонки настроек/проверки роли; expected_version/last_operation обеспечивают CAS и повтор последней операции. Список ограничен 200 последними элементами; масштабирование требует курсорной пагинации.

`capsule-crypto` использует уже установленный Expo SDK 57 Crypto AES-GCM: 256-bit ключ, случайный 12-byte IV и 16-byte tag. Письмо — versioned JSON под ciphertext, вложение — IV/ciphertext/tag в binary. Названия, размеры/MIME и связи — private metadata, не E2EE. Сервер хранит ключ и отдаёт его после password permit, поэтому администраторы backend могут расшифровать данные. Не называть эту схему защитой от владельца инфраструктуры.

Отдельный `family-capsules` bucket private, только application/octet-stream, 50 МиБ + запас на envelope. Storage проверяет frozen owner + owner membership, **не парольный permit**; без permit не получить ключ для расшифровки. Участники не читают даже ciphertext. Нет UPDATE/upsert; DELETE только собственного unlinked объекта, включая защиту архивных капсул. Save проверяет принадлежность ребёнка, UUID/path/type/лимиты, наличие объекта и точный размер plaintext + 28. Не связывать ciphertext с общей `media_files`/галереей.

Экран держит пароль/ключ/permit/черновики только в RAM; async ответы сверяются с epoch, account/family/focus/foreground. Background/expiry закрывают UI, очищают ключ/permit, сохраняют RAM-only черновик/точную pending-операцию до следующего ввода пароля. Blur/unmount/выход сбрасывают черновик. Нет plaintext journal или универсального crash autosave. Picker не использует прежний persistent journal, чтобы не сохранять секретное письмо на диск. Просмотр скачивает ciphertext с bound JWT, проверяет допуск, расшифровывает и открывает через прежние Photo/Video/AudioViewer; свой временный файл/blob удаляет на close/background/unmount. OS crash cache, screenshots, скомпрометированный телефон и сохранённые пользователем оригиналы вне этой защиты.

009/010 уже применены через MCP migration history; не повторять. Обычные Auth, семейные таблицы/медиа и роли не менялись. Корзина капсул — мягкий archive/restore с CAS, не backup и не физическое стирание. Проверки и границы: `docs/CAPSULE_VERIFICATION.md`.

## Актуально: голос дневника и реальные обложки видео — 10 октября 2026

`MemoryAsset` объединяет прежние ImagePicker assets с отдельным `VoiceAsset`; голос — `media_files.media_type='audio'`, а не новый тип воспоминания. Только дневник, один голос на запись, до 3 минут/5 МиБ на клиенте. Все четыре категории допускают голос и требуют текст; только skills допускает фото/видео. Обычная загрузка медиа остаётся без категории. Галереи исключают audio, дневник открывает `AudioViewer` через прежний единственный scope-bound `useMemoryMediaViewer`.

`VoiceRecorder` использует `expo-audio@57.0.5`, `voice-capture` сериализует permission/prepare/start/stop и не позволяет новому экрану обогнать незавершённую подготовку старого. Save/picker блокируются синхронным busy-ref; поздние события не прикрепляются после ухода/смены аккаунта. Запись только по кнопке и в foreground. `AudioPlayback` создаётся только для выбранного файла/черновика, без автозапуска; закрытие синхронно отключает lifetime и ставит pause. React effect replay не блокирует остающийся открытым viewer и не оживляет закрытый.

Прежний upload/journal/reconcile путь работает с голосом, не создавая второй память/файл после потери ответа. Android picker snapshot сохраняет минимальные локальные поля голоса без токенов/байтов. Не считать это универсальным autosave черновика: обычная незавершённая запись может потеряться при завершении процесса. Исходный звук остаётся в приватном cache приложения; автоматического долговременного сборщика несохранённых черновиков нет.

На сервере применены 007 (`20261010090041 diary_voice`) и 008 (`20261010090308 voice_aware_editing`). Первая расширяет прежний atomic invoker RPC, CHECK/частичный unique index и MIME allowlist существующего private bucket. Вторая точечно меняет подсчёт визуальных вложений в существующем CAS-редакторе, сохраняя роли, блокировки и conflict checks. Новых таблиц/API endpoints и ослабления RLS нет; старые строки не переписывались. Повторно SQL не запускать. Серверный CHECK ограничивает размер в metadata; bucket остаётся с общим лимитом 50 МиБ, длительность/реальный кодек на сервере не анализируются.

`video-poster-queue` передаёт массив времён, пробует выбранный и первый кадры, сериализует извлечение, имеет 20-секундный timeout и cache до 16 native references. `video-poster-player` сначала пробует remote кадр, затем при ошибке/пустом результате освобождает remote player и использует единственную HTTPS-only временную локальную копию до 50 МиБ. Завершение/ошибка/фон/unmount удаляют именно её, не чужие файлы; аварийное завершение процесса может оставить cache до очистки ОС. Кадр не сохраняется в Supabase/публичной галерее. Список размонтируется при смене scope, подписанные URL обновляют идентичность; ошибка обложки не запрещает воспроизведение. На web native extraction не заявляется.

Проверки, ограничения, актуальный Android export и ручные сценарии: `docs/VOICE_POSTER_VERIFICATION.md`.

## Предыдущая контрольная точка: дневник и простой плеер — 10 октября 2026

«Записи» используют `MemoryDiaryList`, не общий список медиа. `diary.ts` задаёт четыре категории и совместимость старых текстовых заметок. `FamilyMemoryFeed` фильтрует дневник/категорию на сервере до пагинации; категория входит в scope запроса и курсора. Фото/Видео остаются отдельными коллекциями, общий фильтр ребёнка и права автора/владельца сохранены.

`memory/new` принимает `diary=1/category`: раздел, ребёнок/текст, необязательные вложения только для skills. Категория сохраняется атомарным RPC и в durable submission/picker snapshot. Восстановление прежней отправки приоритетнее нового маршрута. Один файл достижения представлен той же metadata-записью в дневнике и галерее. Старые media не переименовываются; legacy note виден в тёплых моментах.

Живая `20261010072842 diary_categories` добавила nullable `memories.diary_category`, CHECK/частичный индекс и один совместимый RPC с default NULL девятого параметра. SECURITY INVOKER, пустой search_path, authenticated EXECUTE; RLS/Storage/Auth-настройки не менялись. Не повторять SQL 006. `VideoViewer` использует минимальные custom-controls; `video-poster-queue` — один bounded неиграющий извлекатель настоящих кадров с memory-cache списка, отменой и fallback. Прежние privacy/lifetime guards сохранены. Договор, ограничения и проверка: `docs/DIARY_VIDEO_VERIFICATION.md`.

## Историческая контрольная точка: мягкий фиолетовый интерфейс — 10 октября 2026

`FamilyHome` управляет разделами «Фото / Видео / Добавить / Записи / Семья» и общим фильтром ребёнка с текущим возрастом. «Добавить» — действие, а не отдельная пустая вкладка. По последней просьбе владельца галерея больше не разделена по месяцам: `MemoryGallery` показывает непрерывную сетку по две фотографии в строке, в порядке запроса. На главной и странице ребёнка `FamilyMemoryFeed` получает `showDateFilter=false`, `mediaOrder=added`: календарь скрыт, новые загрузки сверху. `MemoryVideoList` — все видео текущих страниц отдельными компактными строками; `MemoryList` — исходные воспоминания. Фото используют `contain`, а не обрезающие обложки. На экране ребёнка доступны те же три режима «Фото / Видео / Записи», в шапке — возраст, не дата рождения.

Фильтрация типа файла не является серверным фильтром: страница без фото/видео не означает конец альбома. Кнопка продолжения сохраняется, пока есть курсор. Ребёнок фильтруется до пагинации прежним запросом; сохранённые даты остаются метаданными. Сервисная поддержка диапазонов дат сохранена для совместимости, но основной UI их не предлагает. Порядок входит в scope запроса: его смена сбрасывает курсор и игнорирует старые ответы. Общий `useMemoryMediaViewer` по-прежнему владеет единственным просмотром над виртуализированным списком и проверяет актуальные объекты/ссылки. Не создавать видеоплееры для каждой строки и не выдавать заглушку за реальный постер. AuthProvider, сервисы записи, схемы и политики Supabase в этом этапе не менялись. Проверка интерфейса: `docs/LAVENDER_INTERFACE_VERIFICATION.md`.

## Реализованный семейный доступ, редактор и корзина — 9 октября 2026

Эта контрольная точка уточняет прежние проектные намерения ниже. Основная архитектура Expo Router + AuthProvider + Supabase сохранена; нового сервера/ORM нет.

- `home`/`child/[id]` передают галерее ID текущего пользователя и признак владельца. Автор записи или владелец открывает `memory/[id]` из списка или полноэкранного фото/видео. При свайпе редактируется запись текущего фото. Доступ повторно проверяет сервер, не только кнопка.
- `memory/[id]`, `family/members`, `family/trash` находятся в существующем family guard. `family/join` — публичная точка ввода кода, без раскрытия семьи до авторизации/принятия. Из setup можно вступить в чужую семью вместо создания новой; из picker/account — принять ещё одно приглашение. Несколько членств поддерживаются прежним выбором семьи; глобального ограничения «одна семья на пользователя» нет.
- Роли текущего этапа: owner управляет приглашениями/членствами и семейными записями; member читает общий альбом, создаёт и правит/архивирует свои записи. Новые приглашения всегда добавляют member. Назначение admin/owner, передача владения и самостоятельный выход из семьи не реализованы.
- `moya_private.family_invitations`: UUID, family_id, created_by, SHA-256 token_hash, created_at/expires_at, revoked_at, accepted_by/accepted_at. Срок 7 дней, максимум 20 активных приглашений, один получатель. Не хранить сырой код в серверных строках/логах. Клиент генерирует 32 случайных байта и передаёт код владельцу через системный Share; это не автоматическая email-рассылка.
- `family-access-service.ts` вызывает create/list/revoke/accept invitation, remove_family_membership, get_memory_lifecycle, set_family_memory_archived, list_family_trash. Запрос связан с исходным аккаунтом и его Authorization; результат после смены пользователя отвергается. Отзыв использует family_members.id, не user_id; повтор старого отзыва не затрагивает новое членство.
- Привилегированная реализация находится в непубликуемой `moya_private`, проверяет auth.uid(), фактическое членство/роль, фиксирует пустой search_path и необходимый порядок блокировок. В public — SECURITY INVOKER RPC-обёртки с EXECUTE только authenticated. Закрытые таблицы имеют RLS без клиентских политик/грантов намеренно, их не нужно открывать для исправления INFO advisors. Не использовать user_metadata как источник прав.
- `memories` дополнена deleted_at/deleted_by/state_version. `set_family_memory_archived` проверяет версию и квитанцию `(user_id,operation_id)` в `moya_private.memory_lifecycle_operations`. Повтор возвращает актуальное состояние и не выполняет прежнее удаление поверх последующего восстановления. Правка увеличивает версию; архивированную запись редактировать нельзя.
- Обычный SELECT RLS скрывает архивированные записи/медиа. Корзина читается через checked RPC: владелец видит все, участник — только свои; страницы 30 + 1 строка-индикатор по `(deleted_at,id)`. Архивирование/восстановление не стирает Storage, записи media_files и отметки детей. Storage DELETE разрешён только собственным несвязанным pending-upload объектам; проверка связей выполняется вне скрывающего архивы RLS.
- `family-operation-journal.ts`: синхронная запись до RPC, ключ привязан к аккаунту/семье/записи. После неизвестного ответа новые параметры блокируются; повтор использует прежние данные/UUID. Правка сверяет исходные/желаемые поля; lifecycle — version + operation_id; приглашение — UUID + token. Явно отклонённый запрос позволяет перечитать/исправить данные. Повреждённый журнал не затирается новой отправкой. Локальное хранилище уже используется Auth, дополнительного шифрования текста/кодов здесь нет.

Не реализованы App/Universal Links с установкой приложения, безвозвратное удаление/автоочистка, backup/экспорт архива, account deletion, granular roles, offline sync и новый дизайн. В Expo Go приглашение можно вставить кодом; custom scheme предназначен для установленной сборки. Signed URL уже открытого файла может работать до истечения срока (сейчас до часа); отзыв доступа не отзывает её мгновенно. Полный отчёт и телефонный чек-лист — `docs/FAMILY_ACCESS_AND_TRASH_VERIFICATION.md` и `docs/SMOKE_TEST.md`.

## 1. Идея приложения

«Моя история» — это приватная цифровая книга жизни ребёнка.

Это не публичная социальная сеть. Это закрытое семейное пространство, где несколько родственников со своими личными аккаунтами совместно создают историю ребёнка.

Основная идея:

Семья → Дети → Память → Фото/Видео → Хронология → Книга жизни

Главная ценность приложения — собрать фотографии, видео и воспоминания о ребёнке в одну организованную историю вместо хаоса в галерее телефона.

---

## 2. Аккаунты

Каждый человек имеет собственный аккаунт.

Например:

- мама
- папа
- бабушка
- дедушка
- тётя
- дядя
- крёстные

Общий семейный логин не используется.

Каждый пользователь входит под своей учётной записью.

---

## 3. Семья

Семья — это приватное пространство, объединяющее родственников.

Одна семья может содержать нескольких детей.

Пример:

Семья Ивановых

- Маша
- Петя
- мама
- папа
- бабушка
- дедушка

Если новый родственник получает приглашение и принимает его, он автоматически становится участником этой семьи и получает доступ к детям семьи согласно своим разрешениям.

При добавлении нового ребёнка существующие участники семьи могут получить к нему доступ без необходимости создавать отдельные приглашения каждому родственнику.

---

## 4. Приглашения

Приглашение отправляется человеку ссылкой.

Сценарий:

1. Мама создаёт семью.
2. Мама приглашает бабушку.
3. Бабушка открывает ссылку.
4. Если приложения нет — устанавливает его.
5. Создаёт собственный аккаунт.
6. Принимает приглашение.
7. Автоматически становится участником семьи.

Приглашение относится к семье, а не к отдельному ребёнку.

В будущем будет система ролей и разрешений.

Предполагаемые роли:

- владелец семьи
- администратор
- обычный участник
- потенциально ограниченный участник

Точная система разрешений будет уточнена позже.

## 5. Дети

Каждый ребёнок является отдельной сущностью.

Основные данные:

- имя
- дата рождения
- фотография
- дополнительные данные в будущем

Дата рождения является ключевым параметром для расчёта возраста.

Приложение самостоятельно рассчитывает возраст ребёнка.

Возраст не хранится как постоянное значение.

Текущий сценарий добавления следующих детей: `/child/new` внутри защищённой семейной навигации. Создаётся только строка `children` в выбранной семье (`id`, `family_id`, `name`, `birth_date`), не новая семья и не новый setup. Поля, defaults, FK, grants и RLS `SELECT/INSERT` подтверждены read-only в живом проекте 7 октября 2026; текущая INSERT-политика разрешает участникам своей семьи, не только владельцу. Фотография профиля, изменение даты рождения и детализированные роли этим этапом не реализованы.

До INSERT приложение сохраняет незавершённую отправку с UUID локально, отдельно для пользователя/семьи. Повтор проверяет ту же строку и её поля, не делает upsert и не заменяет прежнюю отправку новым именем/датой. Неизвестный ответ сохраняет журнал и блокирует редактирование до проверки. После успеха семейные данные заново загружаются AuthProvider; маршрутизацией управляет auth-shell (при нескольких членствах может снова открыться выбор семьи). Локальный журнал не зашифрован, его нельзя очищать вслепую при неизвестном результате.

## 6. Память

Память — центральная сущность приложения.

Память может содержать:

- фотографию
- видео
- текст
- заголовок
- автора
- дату события
- категорию/тип
- одного или нескольких детей

Память автоматически появляется в соответствующих разделах приложения.

Одна физическая фотография или видеозапись не должна дублироваться в хранилище только потому, что она отображается в нескольких местах.

## 7. Главное правило даты и возраста

Пользователь указывает ДАТУ СОБЫТИЯ.

Приложение самостоятельно рассчитывает ВОЗРАСТ ребёнка.

Возраст никогда не вводится пользователем вручную.

Пример:

Дата рождения ребёнка:
10 сентября 2023

Пользователь загружает старую фотографию и указывает:

Дата события:
15 марта 2024

Приложение рассчитывает:

Возраст:
6 месяцев 5 дней

В базе данных сохраняется дата события.

Возраст вычисляется приложением на основании:

дата рождения ребёнка + дата события

---

## 8. Отображение даты пользователю

После сохранения памяти дата события не является главным отображаемым значением.

В готовой книге пользователю показывается возраст ребёнка.

Например:

### 6 месяцев

[фотография]

«Первая прогулка в парке»

или:

### 6 месяцев 5 дней

[фотография]

Дата события используется системой для правильной хронологии, сортировки и расчёта возраста.

---

## 9. Добавление новой памяти

Для новой текстовой памяти приложение использует текущую дату. После выбора фотографий оно автоматически использует доступную дату съёмки, а не дату загрузки.

Например:

Бабушка сегодня сфотографировала ребёнка в парке.

Она нажимает:

«Добавить память»

Выбирает фотографию.

Если в фото есть дата съёмки сегодняшнего дня, она подставляется автоматически.

Пользователь не обязан каждый раз выбирать дату вручную.

---

## 10. Добавление старой памяти

Для архивных фотографий существует отдельный сценарий:

«Добавить старую память»

Пользователь выбирает фотографию или видео из галереи телефона.

После выбора дата съёмки подставляется автоматически, если доступна. Если даты нет, пользователь указывает дату события вручную.

Например:

Фото найдено сегодня, но сделано два года назад.

Пользователь выбирает дату события двухлетней давности.

Приложение рассчитывает возраст ребёнка и помещает память в правильное место хронологии.

---

## 11. Метаданные фотографии

По уточнению владельца от 7 октября 2026 дата съёмки подставляется автоматически из доступного EXIF `DateTimeOriginal`, с сохранением календарного дня камеры. Даты изменения файла, копирования, оцифровки и загрузки не подменяют дату съёмки.

Текущий этап: одно воспоминание имеет одну дату события. Если у выбранных файлов разные даты или у части файлов дата недоступна, приложение явно сообщает об этом и требует общей даты, выбранной пользователем, либо отдельного добавления снимков по дням. Массовое автоматическое разделение альбома пока не реализовано. Видео, скриншоты, пересланные фото и web-picker могут не отдавать EXIF; дату нужно указать вручную. Будущая дата камеры не заменяется сегодняшней молча.

Например:

Дата фотографии:
15.03.2024

Возраст:
6 месяцев 5 дней

Пользователь может:

- оставить дату
- изменить дату

Дата из метаданных не должна считаться абсолютно правильной — пользователь всегда может её исправить.

## 12. Хронология

Главная книга ребёнка строится автоматически на основании реальных дат памяти.

Не создаются отдельные таблицы:

- first_day
- second_day
- first_week
- first_month
- second_month
- years
- months

Вместо этого хранятся реальные даты событий.

Приложение само определяет соответствующий период.

Актуальный интерфейс от 7 октября 2026, после выбора владельцем образца FamilyAlbum:

- основной альбом — календарные месяцы по `event_date`, от новых событий к старым;
- сверху год и горизонтальный выбор месяца, по умолчанию «Все» даты;
- крупная обложка месяца и сетка остальных файлов; каждый файл отображается один раз;
- выбор ребёнка на главной переключает фильтр без ухода с нижней панели;
- текстовые воспоминания доступны отдельно во вкладке «Записи»;
- меню «Моё рождение / первый день / месяцы возраста / годы возраста» убрано из маршрута ребёнка.

Календарный диапазон применяется в Supabase до пагинации: `event_date >= начало` и `event_date < следующий месяц/год`. Семья и выбранный ребёнок остаются обязательными ограничениями запроса. Обложки/месяцы — только представление существующих данных, без таблиц, миграций и копирования файлов. Возраст вычисляется из даты рождения и даты события для подписи, а не для навигационных глав. Прежние утилиты возрастных периодов и их тесты сохранены, но не используются как основной интерфейс.

С 8 октября чтение страниц использует `after`/`nextCursor`, не offset. `memory-pagination.ts` формирует продолжение по полному существующему порядку из даты события, timestamp создания и UUID (для «Записей» timestamp первый). Курсор связан с семьёй, ребёнком, периодом, сортировкой и направлением; значения проверяются до raw `.or()`, timestamp сохраняется без округления микросекунд. `limit + 1` определяет наличие следующей страницы, граница — последняя показанная память. Feed хранит актуальное продолжение в ref; ошибка его не продвигает, refresh/смена scope сбрасывают, поздние страницы игнорируются. Это не snapshot: изменившиеся даты/новые записи перед границей требуют refresh. Серверный RLS остаётся единственной границей доступа. Подробности и ограничения: `docs/ALBUM_PAGINATION_VERIFICATION.md`.

Отображение галереи и «Записей» использует отдельные FlatList, но одновременно смонтирован только выбранный режим. Feed передаёт шапку/календарь, empty/footer, pull-to-refresh и `onEndReached` списку, не оборачивает его в вертикальный ScrollView. GalleryRows разбивает каждый месяц на обложку и строки до трёх файлов; MemoryList — на отдельные воспоминания. Ключи опираются на существующие ID, не индекс строки. Для переменных высот не задаётся фиктивный `getItemLayout`; `removeClippedSubviews=false` выбран как консервативный вариант без агрессивного native clipping. Начальные batch/window параметры требуют измерения на устройстве.

`use-memory-media-viewer.tsx` принадлежит коллекции над ячейками. Он хранит ID выбора, разрешает его по актуальным данным и URL, открывает один PhotoViewer или VideoViewer вне FlatList. MemoryCard в этом режиме делегирует открытие, не владеет Modal/плеером или AppState listener. Выгрузка ячейки не закрывает выбранный просмотр; удаление выбранного объекта из данных, blur/фон закрывают. Scope/key смены семьи/ребёнка/периода/вкладки пересоздаёт коллекцию и сбрасывает просмотр. Удержанные обработчики проверяют время жизни/актуальные объекты/источник. Виртуализация ограничивает смонтированные ячейки, но не накопленный массив данных или метаданные просмотрщика. Подробности: `docs/ALBUM_VIRTUALIZATION_VERIFICATION.md`.

## 13. Семейная лента

Все участники семьи видят новые семейные воспоминания в приватной семейной ленте.

Основная галерея семьи и ребёнка сортируется по `event_date` от новых событий к старым. Архивное фото появляется в месяце события, а не в месяце загрузки. В представлении «Записи» общая семейная лента сохраняет сортировку `created_at` от новых добавлений, а записи ребёнка — по дате события. Файл и дата события не меняются из-за разных представлений.

Ребёнок определяется существующей связью `memory_children`, а не догадкой по фото. На новой форме при единственном ребёнке он отмечен заранее; при нескольких выбор явный. «Вся семья» в форме снимает отметки детей и сохраняет запись только в общем альбоме. Старые записи без связей не перепривязываются автоматически; их можно найти в общей галерее. Точный состав связей конкретных записей владельца на этом этапе не проверялся на сервере.

Например:

Бабушка добавила фотографии с прогулки.

Они автоматически становятся доступны другим участникам семьи согласно разрешениям.

Память одновременно может отображаться:

- в семейной ленте
- в книге ребёнка
- в профиле автора

При этом физический файл хранится один раз.

## 17. Безопасность

Каждая семья является изолированным приватным пространством.

Пользователь не должен иметь доступа к данным другой семьи.

Для этого используется Row Level Security (RLS) в Supabase.

Все основные таблицы должны иметь корректные политики доступа.

Безопасность проектируется сразу, а не добавляется после создания приложения.

## 23. Главная логика продукта

Пользователь не должен думать о структуре базы данных.

Он просто:

1. создаёт семью
2. добавляет ребёнка
3. приглашает родственников
4. добавляет фотографии и видео
5. при необходимости указывает дату события
6. пишет воспоминание

Дальше приложение само:

- рассчитывает возраст
- строит хронологию
- распределяет воспоминания по книге
- показывает семейную ленту
- связывает воспоминание с нужными детьми
- хранит медиафайлы
- обеспечивает приватность семьи

Главная идея:

**Пользователь добавляет воспоминания.  
Приложение само превращает их в книгу жизни ребёнка.**
