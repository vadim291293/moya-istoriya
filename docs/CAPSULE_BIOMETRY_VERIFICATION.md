## Пользовательский результат

- После включения биометрии два отдельных действия: «Войти по отпечатку» (либо «Войти по биометрии») и «Ввести пароль». Биометрия не запускается автоматически при открытии раздела. Ручной пароль не запускает сканирование и не включает биометрию.
- Подключение — отдельная кнопка и отдельный режим: один раз подтвердить существующий пароль капсулы, затем сохранить защищённый доступ на этом телефоне. Это не два обязательных шага каждого входа. Можно включить из закрытой формы или открытого списка. Создание раздела само по себе не включает биометрию.
- Пароль капсулы, подтверждение и пароль аккаунта для восстановления можно показать/скрыть. При фоне/закрытии поля очищаются или вновь скрываются.
- После успешного сохранения явно написано «Капсула сохранена на сервере». Ошибка последующего чтения списка не отменяет подтверждение сохранения. Ошибка чтения больше не маскируется пустым разделом/предложением первого письма; повтор — «Обновить список капсул». Новое письмо недоступно до успешной начальной загрузки.
- При уходе из открытого письма через шапку, системный Back или кнопку списка предлагается остаться и сохранить либо выйти без сохранения. Неизвестный результат отправки сначала требуется проверить. Этот guard не блокирует logout/смену аккаунта; закрытый раздел не раскрывает черновик без повторного допуска.
- Только нажатие «Сохранить капсулу» и подтверждение сервера означают сохранённое письмо. Автосохранение секретных черновиков на диск не добавлялось. Принудительное закрытие/выход из аккаунта может уничтожить несохранённый RAM-черновик.

## Проверка сообщения о пропаже после logout

Read-only запросы живого проекта показали: 1 настроенный vault, 1 активная сохранённая капсула, 0 архивных, 0 капсул без vault; у её зафиксированного владельца текущее owner-членство, всего одно owner-членство в семьях. Содержимое, ключ и пароль не читались. Logout в приложении очищает Auth/локальный биометрический доступ, а не серверные письма.

Это доказывает наличие сохранённой записи на сервере, **но не идентифицирует именно письмо, о котором сообщил пользователь**: его название и факт нажатия сохранения неизвестны. Причину конкретного телефонного показа без воспроизведения не утверждать. Исправлен подтверждённый дефект UI — ошибка чтения могла выглядеть как пустой список. Добавлен тест повторного входа с независимыми экземплярами экрана и общей синтетической серверной записью; это не реальный Auth E2E телефона.

## Защита биометрии

Добавлены только официальные зависимости SDK 57: `expo-local-authentication ~57.0.3`, `expo-secure-store ~57.0.4`; package-lock сохранён, плагины настроены в app.json. Биометрические данные приложение не получает/не хранит.

После успешного **серверного** owner/password unlock дополнительный пароль раздела по явному opt-in хранится в OS Keychain/Keystore с `requireAuthentication: true`, отдельным keychainService и `WHEN_UNLOCKED_THIS_DEVICE_ONLY`. Исключение из прежнего правила «пароли только в RAM» — только этот опциональный защищённый credential, не Supabase пароль, не JWT и не AES-ключ. Marker/index содержат только scope/факт opt-in. Чтение credential требует OS-проверки, а затем обычного серверного unlock. Нельзя заменить это незащищённым storage или проверкой одного клиентского boolean.

- Только strong biometrics; слабое Android-распознавание лица и PIN телефона не запасной способ этой функции. Пароль капсулы доступен отдельно.
- Любой зарегистрированный на телефоне допустимый отпечаток/лицо может пройти проверку. Нельзя определить, родитель это или ребёнок. Если биометрия ребёнка добавлена, использовать только пароль — предупреждение есть перед подключением.
- Scope user/family, синхронная revision-инвалидация и очереди исключают повторное подключение поздней записью после logout. При выходе/смене пользователя credential очищается best effort. После logout для нового подключения нужен пароль снова; серверные капсулы остаются.
- Отмена OS-диалога не стирает opt-in; изменение набора биометрии/инвалидированный ключ требует нового подключения. Ошибка именно `bad_password` удаляет устаревший credential; сеть/лимитер не трактуются как смена пароля.
- Фон/blur/account change/unmount/истечение допуска не позволяют позднему ответу открыть письмо. Ожидаемое iOS inactive от OS-диалога допустимо только пока vault закрыт; реальный background всегда инвалидирует вход.
- На Web биометрия недоступна, секрет не пишется в localStorage. На iOS Expo Go функция намеренно выключена: необходима отдельная сборка с native-конфигурацией.
- Keychain iOS может пережить переустановку. Очистка/OS secure storage не обещают forensic deletion или защиту от root, вредоносной ОС, скриншотов и администратора сервера. Существующее AES-шифрование server-managed, не E2EE.

Официальные источники: [LocalAuthentication SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/local-authentication/), [SecureStore SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/securestore/). Проверены также native Android исходники установленного SecureStore: BIOMETRIC_STRONG + authenticated CryptoObject, без device-passcode fallback.
