## 1. Важнейший дефект: капсула не открывается на Android

**Приоритет P1 — исправить первым.** Пользователь прислал скриншот ошибки `fromCombined`: String вместо ожидаемого native Object. Стек указывает на `decryptCapsuleLetter`.

Подтверждено чтением:

- [capsule-crypto.ts](C:/Users/user/moya-istoriya/src/lib/capsule-crypto.ts:23) передаёт сохранённый ciphertext как Base64-строку в `AESSealedData.fromCombined`.
- Установленный Expo Crypto 57.0.3 в JS допускает `string | Uint8Array | ArrayBuffer` и передаёт строку дальше без преобразования; Android реализация `AesCryptoModule.kt:80` принимает `ByteArray`. На устройстве пользователя такой строковый аргумент отвергается.
- [Тестовая подстановка](C:/Users/user/moya-istoriya/tests/capsule-crypto-mock.cjs:12) сама декодирует строку и потому скрывает несовместимость. Успех roundtrip в Node не является проверкой Android bridge.
- Отдельная проверка настоящей установленной JS-обёртки Expo со строгой подстановкой native-границы воспроизвела отказ строкового аргумента; Uint8Array на той же границе принимается. Использованы только вымышленные байты, без пользовательского ключа/содержимого. Реальный native AES в этой проверке не запускался.

Это наша непокрытая ошибка интеграции. Публичные типы/документация разрешают Base64, но этого оказалось недостаточно для данного Android-вызова. См. [API Crypto SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/crypto/#aessealeddata).

Ошибка возникает до проверки GCM/расшифровки и сама по себе не доказывает повреждения или удаления письма. **Не удалять капсулы, не создавать раздел заново, не менять ключ и не перекодировать серверные строки для устранения этой ошибки.**

Практическое исправление следующим этапом:

1. Безопасно преобразовывать Base64-envelope в байты на стороне клиента перед native fromCombined, сохраняя прежние IV 12/tag 16 и формат хранения.
2. Добавить регрессию на реальную JS-обёртку со строгой native-границей, оставив проверки Unicode, старого ciphertext, неверного ключа и изменения байта.
3. Проверить открытие уже сохранённого письма на Android; затем сохранение → закрытие → повторное открытие → logout/login → открытие того же письма. Вложения проверить отдельно.

**Связанный P2-дефект:** [capsules.tsx](C:/Users/user/moya-istoriya/src/app/family/capsules.tsx:124) выводит произвольный `Error.message`. Скриншот показывает огромный native stack/ciphertext и адрес dev-сервера вместо понятного сообщения. Нужны безопасное пользовательское сообщение и диагностический код без сырого содержимого/ключей/токенов. В текущем проходе это не исправлялось.

## 5. Хранение и безопасность архива

Dashboard: план FREE/NANO, LAST BACKUP — **No backups**. Наличие сторонней копии неизвестно; успешный restore не подтверждён. Нужен backup не только таблиц/ключей, но и файлов обоих Storage bucket с проверенным восстановлением. Резервная копия PostgreSQL сама по себе не содержит байты Storage: [Supabase backups](https://supabase.com/docs/guides/platform/backups).

Остальные границы:

- У капсул server-managed AES, не E2EE: администратор инфраструктуры имеет возможность доступа к ключу. Метаданные названий не зашифрованы. Не обещать недоступность для администратора или сохранность «на сто лет».
- Капсульный RAM pending не переживает завершение процесса гарантированно. Общая медиазагрузка имеет scoped persistent journal и reconcile, но не универсальный долговременный offline-sync и не сохранение любого черновика на каждом нажатии.
- Обычная сессия/журналы хранятся через локальное SQLite localStorage без дополнительного прикладного шифрования; это нужно включить в threat model. Opt-in пароль капсулы находится отдельно в authenticated SecureStore.
- Расшифрованные временные файлы удаляются best effort; crash/ошибка диска могут оставить cache. Нужна безопасная очистка принадлежащих приложению старых файлов и непривязанных ciphertext без удаления подтверждённых вложений.
- Ранее выданная signed URL может действовать до истечения срока после отзыва членства; это нельзя называть мгновенным полным отзывом всех копий.
- Лимит 50 МиБ не заменяет квоты семьи/пользователя, контроль расходов и нагрузочный тест. Постоянных производственных crash reports/уведомлений об ошибках в коде не найдено. Подключать их с исключением писем, токенов, signed URL и паролей из логов.

Дополнительная временная задача: Supabase объявил отключение устаревших CBC TLS 1.2 cipher suites с **10 ноября 2026**. Проверить сетевое подключение на реально поддерживаемых старых Android; не ослаблять TLS и не считать это причиной сегодняшней ошибки. [Официальное изменение](https://supabase.com/changelog/cbc-tls-ciphers-deprecated).

Затем два тестовых пользователя/две семьи: приглашение, принятие, добавление/редактирование/корзина, отзыв; чужая семья и капсула закрыты. Создание данных/письма — отдельный осознанный тест, в этом аудите не выполнялся.

### Шаг 3 — воспроизводимая Android beta

Совместимые patch-обновления SDK с разбором security advisories, идентификатор/подпись/environment, preview APK без Metro. Не делать несовместимый audit fix. Проверить на телефоне и старом допустимом Android: чистый вход, фото/видео/голос, fullscreen/zoom, EXIF, большой файл/обрыв, возврат Android picker, background/перезапуск, связь с ребёнком, капсула/биометрия. Записывать build number, шаги, ожидаемый/фактический результат; не ограничиваться скриншотом ошибки.

### Шаг 4 — защита данных перед внешними тестировщиками

Проверяемые backup и restore DB+Storage, безопасное удаление аккаунта и shared-content lifecycle, сообщения/диагностика без секретов, базовые квоты, review privileged RPC/локального хранения. Индексы/RLS оптимизировать с измерением и повторной проверкой границ доступа.

### Шаг 5 — магазин

Выбрать магазин/страны/тип аккаунта, подготовить privacy/support/deletion URL и декларации, AAB/IPA и тестовый доступ. Сначала internal/closed beta, исправления по фактам, потом публичный выпуск. Разработчик не должен автоматически обещать принятие магазином или точную дату, пока эти условия не пройдены.

## Критерий «можно выпускать»

Нет известного блокирующего дефекта в заявленных функциях; установленная сборка работает без ПК; обычный пользователь может восстановить пароль и вернуться к своему архиву; двухаккаунтные проверки подтверждены; капсула читается после повторного входа; backup реально восстанавливается; удаление/политики/магазинные документы готовы; предупреждения безопасности разобраны; есть подписанный воспроизводимый build и маршрут поддержки.

**Сегодня этот критерий не выполнен.** Следующая небольшая конкретная работа — исправить чтение существующей капсулы и подтвердить его на устройстве, сохраняя данные и текущую архитектуру.
