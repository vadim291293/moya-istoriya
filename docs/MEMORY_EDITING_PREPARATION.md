## Предлагаемый контракт (нуждается в подтверждении перед серверным применением)

Исправляются только заголовок, текст, дата события и полный набор отметок детей. `id`, `family_id`, `author_id`, `created_at` и физические файлы остаются прежними. Тип воспоминания вычисляется сервером из текста и уже существующих медиа, а не принимается произвольно от клиента.

Предлагаемые права: участник редактирует собственную память; точная роль `owner` — любую память своей семьи. Неизвестные роли не получают привилегии владельца. Это **предложение для нового RPC**, не подтверждение готовой полной модели ролей на сервере.

Нужен отдельный `security definer` RPC с пустым search_path: менять детали и отметки атомарно, не выдавая клиенту общих UPDATE/DELETE grants. Членство, роль, авторство и семейность каждого ребёнка проверяются внутри RPC; клиентская проверка лишь помогает UI. На время операции блокируются членство, воспоминание и выбранные дети. Исключение откатывает всю операцию.

В SQL 001 существующая INSERT-политика `memory_children` разрешает участнику добавить отметку ребёнка к любой памяти своей семьи. Поэтому SQL 003 также **сужает эту единственную политику** до автора/владельца. Без этого новый RPC не обеспечил бы заявленную границу для добавления отметок. Старые связи не переписываются. Права работы с `media_files`/Storage этот этап не переопределяет.

## Конфликт и неизвестный ответ

RPC сравнивает актуальные заголовок/текст/дату/набор детей с исходным снимком. Если данные уже равны желаемым, возвращает прежний UUID без повторной записи. Иначе несовпадение исходного снимка — конфликт, без затирки текущей версии. Нельзя после ошибки незаметно заменить исходный снимок новой строкой и повторить старую правку.

Если ответ потерян, сервис читает текущую версию. Совпадение с желаемым означает, что желаемое состояние достигнуто (не доказательство авторства конкретного запроса). Исходная версия при повторном чтении — **результат ещё не подтверждён**, не доказательство отката: первый запрос может ещё выполняться. Повтор допустим только с тем же исходным/желаемым снимком. Другая версия — конфликт.

Это сравнение состояния, а не журнал версий: промежуточная правка, возвращённая точно в прежнее состояние, не различается. История изменений/номер ревизии этим этапом не добавлены. Черновик редактирования не сохраняется на диск; будущая форма должна либо явно описывать это ограничение, либо получить отдельный проверенный журнал перед обещанием восстановления после завершения процесса. Старые журналы создания памяти/Android picker не затрагиваются.

Лимиты клиента — те же 120/4000, что у формы добавления. Проверка сервера считает символы PostgreSQL, а JS — UTF-16; клиент может быть строже для emoji. До 1000 элементов в запросе отметок — ограничение размера payload, не лимит числа детей в семье. Дата — календарный день; сервер допускает максимум текущий день в UTC+14, чтобы не отвергать «сегодня» пользователей впереди UTC, клиент использует свой местный день. Автодата старых файлов и массовое разделение по дням не реализованы этим модулем.
